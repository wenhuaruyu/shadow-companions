# 第三阶段当前交付范围

本次按用户缩小后的范围，实现准备与私密身份，以及从等待准备到第一地点事件的共同阶段推进。小游戏与奖励初稿保存在本地忽略目录 `.runtime/phase3-minigame-draft`，后续设计确认后再接入。

## 原理与数据

Node.js 负责校验业务条件，数据库负责串行裁决和原子持久化。新增 `game_rooms.game_state` 保存阶段、双方确认和私密身份，新增 `game_actions` 保存按房间、座位、请求编号唯一的去重回执。身份采用加密随机数选择座位，一局一名 secret 和一名 courier。

读取以共享行锁取得同一事务内一致的状态、成员和回执。写入以排他行锁重新核对数据库版本，将状态、版本递增、回执在同一事务提交。相同请求和参数优先返回已执行事实，当前快照可随之后的操作前进。同编号不同参数返回冲突。新请求携带旧版本时返回 VERSION_CONFLICT 和 currentVersion。

数据库新函数仅授权 service_role，函数内继续校验网关注入角色。完整状态只到服务端，对外快照使用字段白名单，个人指令仅通过本人鉴权的专用接口返回。普通状态没有身份字段，附带 seat 等身份选择参数的指令请求会拒绝。

## 接口与流程

POST `/api/action` 支持 ready、instruction、tutorial、enter、read，均需本人 Bearer 凭证及 X-Contract-Version=2。动作信封包括 room、requestId、expectedVersion、expectedPhase、kind、data，enter/read 还需 chapter。

准备使用明确 ready 布尔值。双方完成准备时，身份与 brief 阶段一起提交。本人先确认指令再确认教学，双方均完成后进入 map。双方确认 chapter=0 后进入 story，双方已读后进入 event。GET `/api/instruction?room=…` 仅返回本人的 title/text，重复读取保持同一指令。GET state 支持 knownVersion，无变化省略 snapshot。

已有邀请和凭证继续可用。旧房间 game_state 为空时按原 lobby 和初始数值解释，首次动作才写入状态。数据库迁移应先于应用发布。
