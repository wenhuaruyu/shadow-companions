# 七天版本后端实施方案

## 交付范围

以现有两地联网横屏 MVP PRD 为准：七天为开发周期，只实现黄慕兰寓所、铜锣湾避风塘两个可玩节点。五地点地图中的后三处不开放。后端交付双人邀请、私密身份、共同阶段、两类小游戏、资源账本、投入结算、暂停恢复及部署接口。不包含账号、匹配、聊天、最终泄密或骰子对决。

## 技术与部署

沿用仓库的 Node.js、JavaScript ES Modules 和 HTTP API，前后端同域部署。保留现有接口入口，逐步拆分业务代码，避免要求前端一次性重接。

本期部署采用腾讯云 CloudBase 云托管，Node.js 单体服务，独立持久化数据库。数据库采用 CloudBase PostgreSQL，共享环境优先通过服务端 HTTP RPC 调用数据库函数完成事务，原生 pg 驱动用于具备连接入口的环境及本地验收；最终资源选择先核实账号已有数据库和费用，不代表已开通资源。同一事务的所有语句使用同一个数据库连接。

按最多 20 个同时在线房间、40 名玩家验收。游戏新建独立服务、数据库或独立逻辑库与专用权限账号，不覆盖知了服务或业务表。生产优先内网连接，确认云托管和数据库的地域、VPC 及网络配置匹配。数据库连接参数由服务端环境配置提供，不进入前端、仓库或日志。

初期配置最小实例数为 1，避免无流量缩容影响房间计时；最大实例数先设为 1 作为测试基线，压测后再调整。滚动发布仍可能短时存在多个实例，所有房间状态、计时锚点、请求去重和账本必须由数据库持久化并使用事务及行锁协调。内存仅可用于可丢弃缓存；定时结算必须幂等，不依赖某个实例唯一运行。禁止用容器临时 JSON 或 SQLite 文件作为正式存档。暂不引入 Redis 或消息队列。

数据库备份保留策略与恢复演练纳入交付，具体能力和费用在控制台确认。部署还包括连接池上限、健康检查、优雅停止、重启恢复和日志脱敏。域名及 HTTPS 使用 CloudBase 自定义域名入口。

公共状态先沿用轮询，前台每 1000 毫秒一次，请求携带已知版本，无变化返回轻量响应。心跳单独报告页面可见性。反应游戏的本地动画独立运行，服务端校验机会与操作，不依赖公共状态轮询驱动动画。目标是在 PRD 指定网络条件下，两端状态变化两秒内可见。

## 域名与备案并行计划

域名与备案准备已纳入计划，和后端开发同步推进，不作为本地开发的前置条件。购买和实名、备案提交由域名及账号持有人完成；本计划不表示已经购买或提交。

| 阶段 | 工作与完成标准 |
| --- | --- |
| 第一天启动 | 确认已有域名或选择待注册域名；确认腾讯云账号主体、服务器地域和备案资格，决定使用独立域名还是已有域名的子域名 |
| 第一至二天 | 域名持有人完成注册或授权、实名认证；大陆部署按腾讯云当前要求准备并提交 ICP 备案材料 |
| 开发期间 | 后端本地及受控测试并行；跟踪审核结果，按需补充材料，不承诺七天内备案通过 |
| 条件齐备后 | 配置 DNS、HTTPS、同域网页/API 入口和证书续期；邀请链接使用配置的正式公网地址 |
| 发布验收 | 使用正式域名完成双机测试，验证无测试域名提示页、证书有效、邀请地址正确 |

若备案未完成，第七天交付代码和受控测试验收记录，正式域名上线日期单独记录，不把等待备案写成已上线。香港或其他境外部署的备案适用条件需按实际接入方式核对；不为赶工默认改变服务器地域。

## 业务模块

| 模块 | 职责 |
| --- | --- |
| rooms | 创建、邀请有效期、原子占座、准备、终止 |
| auth | 随机本人凭证、凭证摘要验证、本人权限 |
| state | 状态机、双方确认、版本号、公共及本人响应白名单 |
| content | 固定版本的地点、题目、答案、目标配置和规则 |
| attempts | 唯一尝试、有效计时、答题草稿、反应操作、一次性计分 |
| settlement | 资源账本、一次性投入扣除、共同结算、地点解锁 |
| presence | 心跳、后台暂停、双方确认恢复、120 秒恢复窗口 |
| persistence | 数据事务、请求去重、过期清理、重启恢复 |

建议在 `apps/server/src/` 内按上述职责拆分，HTTP 层只做路由、鉴权、输入校验与响应转换。

## 状态与计时

主阶段：等待准备 → 个人指令与教学 → 地图 → 剧情 → 事件 → 投入 → 地点结果 → 下一地点或体验完成。投入不足在地点结果产生时即固定失败，不允许再写入玩法动作；结果阅读确认仅控制展示进度。

暂停是覆盖主阶段的独立状态，记录暂停原因、暂停时间、恢复截止时间及双方恢复确认，不覆盖原阶段。页面后台立即请求暂停；心跳失联按 PRD 的八秒阈值检测。双方在线、页面可见并确认继续后才恢复。屏幕方向不参与判断。

每个尝试保存已消耗有效时长、最近计时锚点及最终结果。用服务端时钟结算时间，暂停期间不增加有效时长。重启后进行中的房间先暂停，禁止凭旧心跳自动继续。恢复窗口从首次进入本次暂停开始计算，单方不断重连不能刷新截止时间。

## 数据与一致性

| 数据 | 主要字段与约束 |
| --- | --- |
| rooms | id、contentVersion、rulesVersion、phase、chapter、version、pause、createdAt、endedAt、endReason |
| players | roomId、seat、tokenHash、role、intelligence、strength、各项确认；座位唯一 |
| attempts | id、roomId、seat、chapter、type、草稿、目标序列、有效时长、score、reward、status；每人每地点唯一 |
| attempt_inputs | attemptId、操作序号、机会编号、输入、服务端接收时间；反应机会首次触控唯一 |
| investments | roomId、seat、chapter、两项投入、确认时间；每人每地点唯一 |
| settlements | roomId、chapter、需求、合计、结果；每地点唯一 |
| resource_ledger | 玩家、属性类型、增减值、来源编号；同一奖励或扣除来源唯一 |
| action_receipts | 请求作用域、requestId、payloadHash、处理结果；作用域内请求编号唯一 |

所有属性写入和业务状态迁移在事务中完成，成功提交后才向客户端确认。事件结束、发奖、写账本为一个事务；投入校验、扣除、写投入和必要的共同结算为一个事务。不得先响应成功再定时落盘。

幂等处理顺序：鉴权 → 查询原请求 → 校验同编号参数一致 → 校验预期版本及阶段 → 执行业务事务 → 保存请求结果。重复请求不再次扣除、发奖或切换准备状态。同编号不同参数报冲突。

版本校验覆盖阶段、资源和确认状态，不随普通心跳递增。两人同时操作时，一方可能收到版本冲突；客户端刷新后确认原动作是否生效，未生效时以新请求编号重新提交。网络重试原请求仍沿用旧编号。尝试输入使用独立操作序号，避免每次点击都与房间全局版本冲突。

创建和加入也需要去重：客户端先生成请求编号和高熵恢复秘密，服务端只存秘密摘要，相同秘密及请求可恢复原座位。邀请标识不具备恢复权限。这样在创建或加入响应丢失时，不需要在去重表中保存明文凭证。

## 接口契约演进

兼容现有 `/api/create`、`/api/join`、`/api/state`、`/api/instruction`、`/api/action`，先更新 `contracts/README.md` 再联调。

普通业务动作增加 `requestId`、`expectedVersion`、`expectedPhase`，地点操作增加 `chapter`，尝试操作携带 `attemptId`。准备改为明确设置 `ready: true/false`，避免重试造成反向切换。新增显式 `resume` 动作。所有玩家身份以凭证解析，不信任客户端提交的 seat。

错误返回统一为 `{ code, message, requestId, currentVersion, retryable }`，按语义区分 400 输入错误、401 凭证无效、404 对局不存在、409 阶段或版本冲突、410 已过期、429 频率超限。保留前端过渡兼容的 `error` 字段。

公共状态只包含阶段、双方属性、公开完成情况、已确认投入、公开记录及连接情况。本人尝试与私密指令单独按本人权限返回。答案、对方草稿、对方身份、凭证摘要和内部账本不得通过对象展开进入响应。

## 小游戏规则

智力：服务端保存正确答案；三题得分对应奖励 0、3、6、10。保存草稿并在提交或超时时一次结算，未答按错。

武力：保留十机会配置和服务端固定目标序列；刷新继续原尝试。每次输入记录机会编号和单调操作序号，服务端核对有效时间窗口、首触及目标区域。错误区域也消耗该机会的首次有效触控，重复请求不增加命中。网络延迟补偿范围需要实机确认并固定，不能接受客户端自行声明的最终命中数。此方案提供合理性校验，不承诺抵御篡改客户端的全部作弊方式。

建立有效尝试和消耗行动点为同一事务。开始失败不扣点，成功后不可换事件或重新生成序列。

## 现有实现需要修补的部分

1. 内存状态每 250 毫秒写 JSON，响应可能早于落盘；改为事务提交后响应，读取损坏存档必须明确报错，不能静默忽略。
2. 已有业务层防重复发奖和投入，但没有完整请求去重；尤其准备当前为取反，需要改为明确赋值。
3. 心跳恢复当前自动解除暂停，需增加双方继续确认及固定恢复窗口。
4. `version` 尚未覆盖加入、计时结束等有效状态变化，也未检查客户端预期版本。
5. 题库直接使用运行时代码，需固定每局内容版本，保留旧局所需内容。
6. 当前按创建时间清理 24 小时，需改为结束后保留 24 小时，并为未开始的邀请独立设置有效期。
7. 当前所有 API 异常均返回 400，需要稳定错误代码、方法校验、输入限长、基础频率限制与敏感日志过滤。

## 七天执行与验收

| 开发日 | 后端交付与检查点 |
| --- | --- |
| 第一天 | 冻结契约、错误码和状态映射；整理现有实现；创建、加入及凭证恢复可联调 |
| 第二天 | PostgreSQL 持久化、请求去重、原子占座、身份隔离和版本冲突；三端抢座仅一端加入成功 |
| 第三天 | 固定版本内容、尝试、有效计时、两类计分和奖励事务；重复提交仅一笔奖励 |
| 第四天 | 投入账本、并发扣除、共同结算和双方继续；第一地点全链路通过 |
| 第五天 | 第二地点、完成与失败终点；后台暂停、双方恢复、重启恢复和结束后保留 |
| 第六天 | 并发、越权、响应丢失重试、超时及崩溃恢复验证；冻结功能 |
| 第七天 | HTTPS 测试部署、两轮真实双机试玩、修复阻断问题、交付 API 与验收记录 |

测试重点：同座位并发加入、身份越权、相同编号不同参数、并发投入、奖励及扣除重复请求、提交成功但响应丢失、事务中断、服务器重启、暂停时超时边界、恢复截止时间、两端结局一致。现有 `npm test` 和 `npm run check` 作为基础检查，不能替代 HTTP 层及实机验收。

部署交付包括环境变量样例、启动命令、云托管与数据库网络配置、数据库备份与恢复说明、健康检查和版本信息。公网发布前必须完成身份隔离、重复结算、可靠恢复及两机完整流程验收。
